# YunShu 容器透明网关改造思路

## 1. 背景

当前 `yunshu-nix` 的形态是：

```text
局域网设备
      |
      v
容器 IP:7890（3proxy，HTTP / SOCKS）
      |
      v
容器内的 YunShu TUN / VPN
```

这个形态只能作为**应用层代理节点**，不能直接作为局域网默认网关。如果继续用
socks/http 代理覆盖所有流量，就需要在主路由或应用层代理中再实现一套分流策略，
再通过 tproxy / fwmark / NAT 把流量导回代理，配置复杂且和 YunShu 自带策略重复。

## 2. 结论

更合理的改造方向是：**把 YunShu 容器从“代理节点”升级成“透明网关”，直接复用
YunShu 自带的 TUN 和分流策略。**

目标形态：

```text
局域网设备
   默认网关 = 192.168.10.3
        |
        v
   yunshu-router 容器
        |
        v
   YunShu 自带的 TUN + redirect_nets / ignore_nets 策略
        |
        v
      VPN / 直连
```

这样不需要在外面再做一套应用层代理/tproxy 策略，也不需要让每台设备显式配置
HTTP/SOCKS 代理。

## 3. 为什么 YunShu 适合走 TUN 网关路线

从 headless payload 可以确认 YunShu 不只是简单代理，而是自带策略引擎：

- `libtunnel.so` 导出 `StartTun`、`StopTun`、`StartLocalProxy` 等接口；
- 配置字段包含 `routes`、`ia_redirect_nets`、`pa_redirect_nets`、
  `ib_redirect_nets`、`ignore_nets`、`socket-mark-value`、`dns-listen-addr`、
  `local-port-*`；
- `yunshu-daemon` 包含 `tun_worker`、rtnetlink 路由监控，以及
  `ip route add/del`、`0.0.0.0/0`、`128.0.0.0/1` 等默认分流路由逻辑。

也就是说，策略分流应该由 YunShu 自己完成，网关层只需要负责把局域网流量正确
交给 YunShu 的 TUN，再正确回程即可。

## 4. 当前配置的差距

### 4.1 网络能力

当前 `modules/container.nix` 已具备：

- `privateNetwork = true`
- `enableTun = true`
- bridge 模式下独立 LAN IP
- 可选的 nat 模式

但缺少：

- `net.ipv4.ip_forward = 1`
- IPv6 forwarding
- 容器内转发防火墙规则
- 从 eth0 到 YunShu TUN 的入站/回程转发

### 4.2 代理层

当前代理能力由 `modules/proxy.nix` 提供，`private_proxy` / `public_proxy` mode 按需启用 3proxy。透明网关模式下，
这个代理入口不是必需的，反而会引入第二层策略。

当前代理还存在安全面问题：

- `auth = [ "none" ]`
- `denyPrivate = false`
- 监听 `0.0.0.0`

如果切换成网关模式，应优先移除或收紧这个公开代理。

### 4.3 DNS

YunShu 自带 DNS / DoH 策略，但局域网客户端默认 DNS 仍可能绕过容器，导致
域名分流不一致。透明网关必须明确 DNS 入口。

## 5. 改造方案草案

### 5.1 启用转发

在容器 guest 内开启三层转发：

```nix
boot.kernel.sysctl = {
  "net.ipv4.ip_forward" = true;
  "net.ipv6.conf.all.forwarding" = true;
};
```

### 5.2 放行转发流量

在容器内放行 LAN 到 TUN 的转发和回程流量。接口名需要按实际环境确认：

```nix
networking.firewall.extraForwardRules = ''
  iptables -A FORWARD -i eth0 -o tun0 -j ACCEPT
  iptables -A FORWARD -i tun0 -o eth0 -m state --state RELATED,ESTABLISHED -j ACCEPT
'';
```

> 如果 YunShu 使用的 TUN 接口名不是 `tun0`，以容器内实际接口为准。

### 5.3 去除或收紧代理层

透明网关模式下，可以先关闭 `services.yunshu.proxy`：

```nix
services.yunshu.proxy.enable = false;
```

如果暂时保留代理作为调试入口，也应限制监听地址或加访问控制，不要继续使用
`0.0.0.0 + auth none` 的默认值。

### 5.4 规划 DNS

优先让局域网设备使用容器作为 DNS，或由容器内做 DNS 重定向。具体需要确认：

- YunShu 的 DNS 监听地址和端口；
- 客户端是通过 DHCP 下发 DNS，还是手工配置；
- 是否需要为 53 端口做透明重定向。

### 5.5 调整局域网客户端

在 DHCP 或路由器上把客户端默认网关指向容器 LAN IP，例如：

```text
gateway = 192.168.10.3
dns     = 192.168.10.3
```

### 5.6 必要时做 SNAT

如果验证发现 YunShu TUN 不接受来自局域网客户端的原始源地址，需要在容器内对
进入 TUN 的流量做 SNAT：

```nix
networking.firewall.extraCommands = ''
  iptables -t nat -A POSTROUTING -o tun0 -j MASQUERADE
'';
```

但这应作为最后手段，先验证再决定，避免破坏 YunShu 自身的分流和回程逻辑。

## 6. 验证清单

1. 容器内确认：

   ```sh
   sudo nixos-container run yunshu-router -- sysctl net.ipv4.ip_forward
   sudo nixos-container run yunshu-router -- ip addr
   sudo nixos-container run yunshu-router -- ip route
   sudo nixos-container run yunshu-router -- ip rule
   ```

2. 确认 YunShu 创建了预期 TUN 接口，并正确安装策略路由：

   ```sh
   sudo nixos-container run yunshu-router -- ip route get 8.8.8.8
   ```

3. 让一台局域网测试机把默认网关指向容器 IP，观察：

   ```sh
   ip route add default via 192.168.10.3 dev eth0
   ```

4. 分别测试应走 VPN 和应直连的目标，验证分流策略是否由 YunShu 正确执行。

5. 在容器内抓包确认 eth0 和 TUN 的收发方向：

   ```sh
   sudo nixos-container run yunshu-router -- \
     tcpdump -ni eth0 -n
   sudo nixos-container run yunshu-router -- \
     tcpdump -ni tun0 -n
   ```

6. 测试 DNS：确认域名解析路径和分流结果一致。

## 7. 需要确认的风险点

- YunShu 的 TUN 是否接受从 eth0 转发进来的第三方源地址；
- YunShu 下发的 `redirect_nets` / `ignore_nets` 在容器 netns 中是否覆盖局域网流量；
- YunShu 是否会对进程或 fwmark 做排除，导致转发流量被绕过；
- 宿主机 bridge、防火墙和 NixOS 容器网络是否会影响转发；
- IPv6 是否需要同步规划；
- 如果启用透明网关，应移除或严格控制原来的 7890 代理入口。


## 8. 已完成的透明网关 POC 结果

测试时间：2026-08-27。

测试环境不是 NixOS 容器，而是在 Arch Linux 上用 Docker 模拟网关链路，用于验证
核心网络路径：

```text
lan-client: 172.30.0.20
      |
      | default gateway
      v
yunshu-gw: 172.30.0.10
      |
      v
YunShu tun0: 10.251.1.1
```

关键环境参数：

- `yunshu-gw` 开启 `NET_ADMIN`、`NET_RAW`、`/dev/net/tun`
- `yunshu-gw` 开启 `net.ipv4.ip_forward = 1`
- `yunshu-gw` 关闭 `rp_filter`
- YunShu 通过飞书登录成功，并执行 `yunshu -s all`
- `lan-client` 默认网关指向 `172.30.0.10`

验证结果：

| 测试项 | 结果 |
| --- | --- |
| `ping 10.11.5.52`，经 yunshu-gw 进入 YunShu TUN | 3/3 成功，ttl 62，延迟约 52–157ms |
| `ping 10.4.23.1`，经 yunshu-gw 进入 YunShu TUN | 无回复，但抓包确认请求已进入 `tun0` |
| `curl http://1.1.1.1`，经 yunshu-gw 直连 | 成功返回 301 |

抓包证据：

```text
tun0 / eth0:
IP 172.30.0.20 > 10.11.5.52: ICMP echo request
IP 10.11.5.52 > 172.30.0.20: ICMP echo reply
```

结论：

1. YunShu TUN 接受从 `eth0` 转发进来的第三方源地址，透明网关核心路径可行；
2. YunShu 会自行维护 VPN 路由，容器只负责三层转发，不需要额外代理分流；
3. 直连流量在当前 Docker 测试中会触发 ICMP redirect，生产配置需要关闭
   `send_redirects`；
4. DNS 入口仍需要单独处理。

下一步：

- 在 `modules/container.nix` 增加 `mode` 枚举（`gateway` / `private_proxy`）；
- 开启 IP 转发并关闭 ICMP redirect；
- 放行容器内 `eth0 <-> tun0` 的转发流量；
- 网关模式下关闭 `services.yunshu.proxy`，避免保留公开 7890 代理。


## 9. 初版改造状态

以下改动已经落到仓库中：

- `modules/container.nix` 新增 `yunshu.container.mode`，各 mode 独立为 `modules/modes/*.nix`；
- `mode = "gateway"` 时启用 IPv4/IPv6 转发、关闭 rp_filter 和 ICMP redirect；
- 使用 nftables 防火墙放行 `eth0` 与 `tun0` 的转发流量；
- 网关模式下强制关闭 `services.yunshu.proxy`，避免继续暴露 7890 代理；
- `flake.nix` 的 `nixosModules.container` 默认使用 `mode = "gateway"`；
- `examples/container-flake.nix`、README 和使用手册已同步为网关示例。

尚未完成：

- DNS 透明转发/局域网 DNS 入口；
- 网关模式下的访问控制细化；
- 真实 NixOS host 上的完整部署验证。
